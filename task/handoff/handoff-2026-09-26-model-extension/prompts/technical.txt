Review the following design for a small database running on a mobile device. Explain how the recovery protocol should behave if the process stops between writing a transaction record and updating an index. The database must support a single writer and several readers. A reader should observe either the old committed version or the new committed version, never an intermediate mixture. The storage device can reorder writes unless an explicit durability barrier is issued. Memory is limited, so the design cannot keep a complete duplicate of the database while preparing every transaction. The application can tolerate a slow restart, but it cannot accept silent loss of a transaction that has already been acknowledged as durable.

The proposed design uses three files. The data file contains immutable pages, the journal stores transaction records, and the manifest identifies the latest committed root page. Each journal record has a monotonically increasing sequence number, a checksum, a list of newly written page identifiers, and the identifier of the previous committed root. A transaction first creates new data pages in unused space. It then appends a journal record describing those pages. After the data pages and journal record have reached durable storage, the writer publishes a new manifest. The old pages remain available until no reader holds a snapshot that references them. A background process later reclaims their space.

Consider the following pseudocode. The function write_pages does not guarantee durability by itself. The append_record function can return after the operating system has accepted the bytes into its cache. The publish_root function writes a short manifest, but that write may be interrupted. The system therefore stores two manifest slots, each with a generation number and a checksum. Recovery reads both slots, rejects invalid checksums, and chooses the most recent generation whose referenced journal record and data pages are complete.

function commit(transaction):
    next_generation = current_generation + 1
    pages = build_copy_on_write_pages(transaction)
    write_pages(pages)
    append_record(next_generation, pages, old_root)
    flush_data_and_journal()
    publish_root(next_generation, pages.root)
    flush_manifest()
    acknowledge_commit()

There are several questions to examine. If writing a page succeeds but the journal record is incomplete, recovery must not expose that page as part of a committed tree. If the journal is complete but neither manifest points at the new generation, the protocol must define whether replay can commit the transaction or whether it should retain the previous state. That decision must be consistent with the acknowledgement rule. If the new manifest is durable but an old snapshot is still active, reclamation must wait for the reader. If a checksum is valid but a page references a generation that never committed, structural validation should detect the inconsistency rather than following an arbitrary address.

The index is a tree whose leaves contain key and value pairs. Internal nodes contain separators and child page identifiers. A page update creates a new path from the modified leaf to the root. Multiple updates in one transaction may share unchanged subtrees. Readers pin a root generation at the start of a query. The writer records retired pages together with the generation in which they became unreachable. Reclamation compares these generations with the oldest active reader. A reader that is stalled indefinitely may prevent space reuse, so the application needs a policy for cancelling long-running queries or placing a limit on their snapshot lifetime.

The system should distinguish logical correctness from performance. Larger write batches can reduce the number of durability barriers, but they also increase commit latency for individual transactions. Compressing pages can reduce storage traffic, while consuming CPU time and introducing variable page sizes. Keeping a larger cache may improve repeated queries, but it reduces memory available to other applications. A performance experiment should measure median and tail commit latency, bytes written per logical update, restart time after interruption, and the amount of space retained by old readers. It should also report the hardware, file-system settings, and whether the measurements include initial file allocation.

Finally, propose a fault-injection plan. Interrupt execution before and after each durability barrier, truncate the last journal record at several offsets, corrupt one manifest slot, and restart while a background compaction operation is incomplete. For each case, state which generations may become visible and which must remain invisible. Explain how the expected result changes if the application requests only atomicity without durability. Include a discussion of why a successful memory copy or a completed asynchronous write callback is not necessarily evidence that data has reached persistent storage. Separate guarantees provided by the database from assumptions made about the operating system and the storage device.

Additional calibration workload specification. A benchmark coordinator owns the experiment queue and records the exact executable, library, model, and configuration hashes before each run. The coordinator distinguishes model preparation from resident inference, because a fast warmed execution is not a measurement of first-request latency. Each record includes input length, requested output positions, active devices, actual routed pairs, intermediate storage capacity, and synchronization boundaries. Report all successful repeats and preserve failed runs with their failure reason. Do not silently discard a slow run merely because it contains a page fault.

When examining matrix workloads, describe both the logical rows and the rows the backend actually computes after alignment or packing. Two groups with the same total number of token-expert pairs may differ in active expert count, maximum group size, padding waste, and traversal overhead. Shared experts process all tokens, while routed experts see sparse and uneven subsets. Timing one expert in isolation does not establish the performance of several expert groups running concurrently with a shared branch. Measure the critical path, including gathering, launch, completion, and reduction, in the execution environment where it will be used.

A reusable activation pool requires a clear lifetime contract. Inputs must remain valid until their last consumer completes. Outputs consumed by host aggregation must remain valid after the device graph finishes. Views share the storage of their base tensor, so ending the lifetime of a view does not establish that the underlying allocation is dead. Within a node, an output should not overwrite an input unless the backend explicitly supports that operation in place. Across sequential layers, graph metadata may remain cached while the same activation backing is reused after synchronization. Ownership of imported handles must outlive every graph referencing the memory.

The experiment should separate placement decisions from weight preparation. A candidate whose weights are absent cannot execute for free. The scheduler may reject it or account for an explicit preparation cost supplied by a separate component. A compact model can predict group execution and synchronization without learning the internal algorithm of every weight converter. When evaluating a new input length, calibrate only with the designated training input, freeze the resulting parameters, and then evaluate different inputs. Interpolation between measured lengths is a hypothesis to test, not an automatic guarantee of accuracy.
