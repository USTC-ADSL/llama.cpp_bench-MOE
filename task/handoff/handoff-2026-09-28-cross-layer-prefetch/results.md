# 跨层权重预转换：机制有效，尚未超过常驻 NPU

范围：fd8657d6，Qwen1.5-MoE Q4_0，128-token 单请求完整 Transformer 首次 prefill。模型已加载，输出层已恢复驻留，目标 Expert 转换缓存为空；计时包含真实在线路由、转换、同步、attention 和聚合。没有目标 prompt 的路由预跑或重放。两份新输入各三轮、每次新进程，以 native/online/prefetch 轮换顺序测量。配置在确认集执行前冻结，见 `confirmation-plan.json`。

## 原型与预测

第 L 层 GPU 完成 shared Expert 后，后台 GPU 将下一层的最多 K 个 routed Expert 从 canonical Q4_0 转换到 HTP packed 布局，写入共享 DMA 双缓冲。CPU/NPU 继续当前层计算。下一层只在缓存已完成时使用它；未完成或未命中仍以真实 router 分配从 canonical 源计算，不等待猜测结果。下一次 GPU 调用前需要 join，避免同一 OpenCL queue/kernel 参数并发修改。该等待单独记录。

预测目标是“下一层实际交给 NPU 的 Expert”，不是“是否有任意 token 激活”。训练六份 prompt、独立预测验证两份；仅以训练集留一验证选方法。逐层先验优于相邻层同编号计数以及当前层条件 ridge 修正：验证 precision@4 为98.86%，同编号方法仅40.91%–50%；相邻同编号计数相关约0.014–0.017。当前证据支持**逐层稳定热点**，没有证明“同编号跨层相似”。本原型是提前准备下一层的固定统计先验，尚未采用上下文条件预测。

六次配对的预取版本均快于未预取版本，151,936 个 logits 逐字节相同，24 层路由计数和分配完全相同。每组仅三次，且 native 存在较大跨进程波动，不声称统计显著性或全面在线加速。跨后端原生/异构仍不逐值相同：两个输入 relative-L2 分别7.61%/3.21%，top-1 相同；新增预取不引入额外误差，不等于原有跨后端质量差异已经解决。

## 为什么有效，为什么收益有限

1. **真正出现重叠。** K8 每次准备176个 Expert，lighthouse 实际 NPU 预测命中154个、及时使用142–147个，20–21/22层就绪；textiles 命中并使用163个，22/22层就绪。准备总墙钟约163–170ms，其中约68%–74%与当前层 CPU/NPU 分支墙钟相交，剩余还可能覆盖层间工作。该相交不是独立 GPU kernel 利用率，也不能直接等同于节省时间。GPU 暴露 join 总计0.001–4.521ms。
2. **转换阶段下降，但分图增加。** 开发输入单独 PROFILE=3 诊断，同路由/分配/logits：未预取 canonical routed DSP op358.920ms；预取 canonical291.085+packed42.225=333.310ms。主线程权重阶段230.73→202.91ms，DMA暴露等待66.09→67.09ms，HMX等待19.12→19.22ms。主线程权重阶段含worker dispatch，不是纯算术时间。命中/未命中分图使被跟踪MATMUL_ID实例46→90，不能把所有剩余开销解释为复制。profiling仅用于归因，不作为吞吐测量。
3. **CPU 会接近关键路径。** lighthouse 的分支累计中位值：NPU420.90→392.24ms，CPU383.71→385.66ms；textiles：NPU416.46→383.99ms，CPU387.04→393.13ms。这些跨层和不能代替逐层 max，但解释了继续加速 NPU 为何不会等量变成整模型收益。当前分配器尚未计入缓存命中后的 NPU 成本下降。
4. **预取过多会侵占下一层。** 开发输入单次 K4/K8/K12：600.65/574.27/643.98ms，就绪层数22/20/8；K12 GPU join累计76.55ms。K12 准备264个但及时使用仅81个。该开发消融支持控制窗口，不能充当独立最终收益。

## 内存边界

只保留一份完整 canonical 源：routed约6682.5MiB，shared约445.59MiB。CPU别名源，NPU从canonical按需计算。新增双槽packed容量：K4/K8/K12为37.125/74.25/111.375MiB；不保留全模型三端副本。K8确认的进程峰值RSS约834.7–837.1MiB，不包含全部DMA。

OpenCL observer 对导入的已有278.44MiB源DMA又按容量收费，raw scoped allowance为424.45MiB；仅去除这个已知源别名后为146.01MiB。两个目标DMA的容量通过常驻OpenCL导入仍计入该数，不能再把74.25MiB当成独立副本重复相加。RPCMEM采用charged覆盖，OpenCL采用extra覆盖。这个数字是有限范围的容量账本，不是完整物理峰值证明；driver内部、dense/KV、文件页缓存及未跟踪分配另有边界，约200MiB的总额外物理内存验收仍未完成。

## 下一阶段优先级

1. **混合布局单图执行。** 在一次 routed 图/算子中按 Expert 选择 canonical 或 packed 地址，保留相同聚合顺序，减少命中/未命中双图的提交和激活准备成本。先以固定分配消融，防止与调度变化混淆。
2. **窗口约束的预取量与分配联合决策。** 使用当前已观测完成时间预测可用窗口 W；按“到达NPU的概率×省下的关键路径时间”排序，满足预计准备时间+余量≤W、双槽内存预算，允许某层K=0。再以当前已就绪缓存修正NPU分组成本，避免CPU成为新长尾。先验是基线，条件预测仅在独立验证有净收益时增加。
3. **增量就绪。** 当前三矩阵全部完成才发布整个槽；研究按Expert/小组发布与消费，降低因一小段尾部转换未完导致全组回退的浪费。必须保持单槽写入与NPU读取的范围、同步和格式可见性正确。
