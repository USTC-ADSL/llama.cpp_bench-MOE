# TODO 2：基于当前路由的整专家异构调度

独立确认实验已完成，40个计时进程、240次完整模型 prefill；原生/同路径全 NPU/三路归因对照另行执行，不用于重新拟合或修改冻结确认结果。实现检查点：1507efd24。

## 方法与论文表述

这里的设备调度器不改变 MoE gate 给出的 top-4 专家及其概率。它在每层拿到实际专家 ID 后，统计每个专家的 token 数，将一个专家的全部计算分配到一个后端；shared expert 单独选择后端。CPU、GPU、NPU 分支异步并行，最后按原 top-4 顺序合并结果。

成本模型分别预测三个后端执行一组专家的时间，而不是假设“所有专家延迟相加”或者“所有专家完全并行”。CPU 按专家组织矩阵块并在线程间分工；NPU 的 HMX 路径逐个处理活跃专家；GPU 的 MoE kernel 可以通过 work-group 并行处理不同专家的计算块。这些不同的执行方式由后端专属的回归模型和分组特征描述。

特征包括各后端的 token–expert pair 总数、活跃专家数、每专家 token 数分布、8/32 对齐后的工作量、最大专家负载、实际驻留 bank 宽度、native/split 形状、shared 工作量和其他并行分支的负载。每个后端26维特征，主机开销8维。特征不包含专家 ID、层号或 prompt ID。先按特征尺度归一化，再使用带非负约束和相对误差权重的 Ridge 回归；非负约束用于避免搜索利用不合理的负工作量系数。

对于分配方案 \(P\)，调度目标为：

\[
\widehat T(P)=\max_{b\in\{CPU,NPU,GPU\}}\widehat T_b(P)+\widehat T_{host}(P).
\]

搜索从若干初始分配出发，尝试迁移整个专家、交换两个专家、移动 shared，以及联合移动 shared 和一个专家。初始方案包含旧调度和三路分配，但不是最终分配的限制。使用确定性的两起点局部搜索，每层最多2048次估值；不声称找到全局最优。实际实现位于 tests/moe-route-scheduler.h，在线接入位于 tests/fullmodel-oracle.cpp。

## 驻留假设与计时边界

为隔离 TODO 1，布局转换与驻留准备在正式推理计时前完成。准备器根据冻结模型构造有限驻留集合：紧凑最优分配、每层6个备用专家布局，以及约束 shared 后重新优化所得预测时间在最优值20%以内的 shared 布局。正式 callback 只依据本次实际 ID、冻结成本系数和明确的可用布局集合重新搜索；缺少布局的分配不可选。物理 bank 宽度会参与估值。

因此这是**有限布局预备好条件下的当前路由调度**，不是全部专家在三个后端都有副本，也不是陌生请求的冷启动性能。准备阶段可以利用 CPU 路由捕获来决定布局，正式执行仍重新计算 gate/top-k；捕获 ID 只用于准备和事后差异诊断，不替换实际路由。准备时间、逻辑权重字节数、activation pool 和推理时间分别记录。

完整模型时间覆盖24层 prefill、实际路由、每层调度、分支执行/同步、聚合、最后 token 的 logits 和保留 KV；上下文清理与权重准备在计时外。每层 gather、expert wall、combine 是依次记录的三个 wall-time 窗口。开启 overlap gather 后，分支的数据整理位于 expert wall 内；三个后端的服务窗口彼此重叠，不能相加作为延迟。

E2E 减去上述每层窗口之和只能称为“未被 FFN callback 窗口覆盖的时间”，还包含 router/top-k、回调包装、图调度/复制、残差相加、attention、输出投影/logits 和诊断构造，不能直接叫 attention 时间。

## 校准、对照与适用范围

设备为 fd8657d6（Redmi K80 Pro），模型为 Qwen1.5-MoE-A2.7B-Chat Q4_0。使用128、768、1536的开发输入，包含匹配当前 lifetime arena/fused reduction/overlap gather 路径的分支 profile 和既有 technical 完整模型开发记录，共501个校准点。Ridge alpha=.03；开发拟合总时间 MAPE9.44%，CPU/NPU/GPU 分支 MAPE25.80%/6.22%/5.19%。CPU 误差仍较大。

冻结后使用 museum/cooperative 两个新主题，确认768，再验证128和未参与拟合的1024/2048。每方案运行两个独立进程，顺序互为逆序，每进程2次 warmup、6次计时；不删除慢样本。对照为原生全 NPU、固定 c8/g15 三路、旧 CPU-tail4/sharedGPU。除原生路径外，对照使用同样的共享激活、生命周期复用、直接 callback IO、融合聚合和重叠 gather。

模型仅针对这台设备、这个模型/量化格式及执行路径校准；有限的新主题和长度测试不能证明跨模型、跨设备或所有输入的泛化。

## 已核实的实现正确性

- Host 契约测试覆盖小规模穷举最优、当前路由敏感性、预算、shared 三后端、缺失布局和未激活专家的可用性约束。
- Android resident-contract 覆盖12种 native/shared/三路组合；共享驻留集合与新建紧凑布局的输出差异为0；倒序访问15个缓存图时输出逐位一致且无新增分配。
- 原有 placement model 的4项契约测试通过。
- 768开发输入第16层的全 NPU/全 GPU 与部分异构方案都在同一个 token 上略超既有4%阈值（约4.09%），并非异构方案独有；不将这些记录描述为全部阈值检查通过。完整模型另报告 logits 差异和重复一致性，不将其当作困惑度或下游质量等价证明。

## 长输入的内存问题

最初无条件保留三个 shared 后端副本时，1536出现每轮38410–109000次 major fault，延迟2127.14ms。减少没有竞争力的备用 shared 布局后，自建权重 bank 从8.484降到7.614GiB，activation pool 从576.47降到420.47MiB；6轮 major fault 均为0，延迟1890.91ms。这里的 bank 字节数不等于设备总内存占用，另有基础模型、上下文及驱动开销。

详细证据见 docs/bugs/2026-09-28-route-residency-pressure.md 及本目录 handoff-03-development-freeze.md。

数值与运行时审计：所有 custom 确认进程的逐轮 logits 逐位一致、warmup 后图分配计数稳定，route 的真实 pairs、当前 owner、shared 与驻留可用性均匹配。所有方案的两个进程最后 token logits 逐位一致。route 相对 native 最后 token logits 的 relative L2，按上表输入次序为4.40%、2.86%、3.73%、3.12%、3.65%；top1均一致。这不等于下游质量等价。
