## 任务及实际内存

同一 fd8657d6（Redmi K80 Pro），沿用原模型、最佳 B1 全层 OpenCL `-ngl99`、相同 512 输入/128 输出。两任务各三对 noLLM/LLM，顺序 AB/BA/AB，先图片后 PDF；[协议](protocol-heavy.md)在正式运行前固定。

| 新增任务 | 独立 noLLM 诊断 PSS | 保护状态与继续操作 |
|---|---:|---|
| 多看 8.4.19，160 页栅格 PDF，约116 MiB | 就绪321 MiB；后台257 MiB | 返回仍为81/160页，并继续到后续页 |
| 小米图片编辑器 2.4.0.2.1，8000×6000 / 48MP 图片 | 就绪172 MiB；后台110 MiB；导出采样峰值 **1.045 GiB** | 未保存红色标记保留，导出同尺寸且含标记的新图片 |

**用户提出的担忧成立：素材大不等于驻留内存大。** PDF 分页、图片预览降采样使后台占用仍为几百 MiB；真实全尺寸导出才出现约1 GiB短暂峰值。该峰值来自独立诊断的15个样本，不是严格上界，也不证明正式 LLM 共存时的峰值大小。未取得可用的原轻量 App PSS 对照，不作其内存倍率比较。

## 六对结果

延迟为恢复已有任务后观察到的首个合格 HWUI 帧完成时间，**不是完整画面呈现/内容加载时间**。不发新的文件打开 Intent。退化仍须同时增加≥500 ms且≥50%，或新增 reload；状态丢失/任务中断为失败。没有随结果改阈值。

六对均变慢，不能写成“无影响”；但均未达500 ms绝对增量门槛。12次切回的目标 PID 均与后台时相同，未观察到返回时重启。六次 LLM 的128个输出 token 与原CPU逐项一致，512输入/cache0、trace无溢出，切回均发生在推理请求内。

图片导出三对耗时分别为 **2.285→2.849、2.250→2.909、2.272→2.803 秒**（约+23%～29%，辅助观察，不把导出耗时冒充切回指标）。实际导出与推理重叠1.59～1.74秒，并非覆盖导出全程或证明峰值必然重叠。LLM条件最低 MemAvailable：图片1.727～1.878 GiB、PDF2.377～2.478 GiB；thermal均0，无安全停止。内存值不与模型PSS/KGSL相加。

## 取证修正、边界与收尾

原始图片 LLM `continuation_ok=false` 是**异步导出早查**：推理已结束而导出尚未完成。未重跑，保留原记录；延后读取同一 PID、同一路径的完成日志，并校验实际8000×6000输出/红色标记/SHA256，三次均成功。最终结论使用 `export-followup`，不是将缺失记录直接改成成功；详见[分析数据](evidence/heavy/analysis.json)及[CSV](evidence/heavy/summary.csv)。

状态确认上界含截图/UI工具开销：图片约4.7～4.9秒，PDF约7.9～8.2秒，均小于10秒，但不等于实际恢复耗时。noLLM后台等待46秒，LLM加载27.26～40.76秒，并非精确等待配平；不清文件缓存。仍继承ADB启动/系统优先级边界，不能代表普通Android LLM App或低内存设备。

**结论：新增两个真实任务后仍未发现达到预设门槛的共存失败，但观察到稳定交互减速及导出减速。** 证据范围扩大到分页阅读和短暂高内存导出，不支持“所有重App都能共存”，也不支持“现有方案无法与真实App共存”。按用户要求到此停止，不扩充实验量。
